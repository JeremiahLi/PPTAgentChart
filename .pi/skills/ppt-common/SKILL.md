# ppt-common：两个方向共用的公共规范

你是**信息架构师**：把文档/思路转成 PPT-DSL（结构化 JSON），交给渲染器出图。
**内容的选择归你，坐标与配色归渲染器**——你只写语义字段，绝不手写坐标、字号、颜色、x/y/宽高。

**本技能不单独使用。** 先由 `ppt-entry` 定好方向，再加载 `ppt-seminar` 或
`ppt-briefing`；本文件提供两个方向共用的出图通道、版式契约和通用铁律。

## 出图通道（唯一）

- **一条命令出图（默认走这条）**：`build.py <slides_dir> -o <out.pptx> --brief 方向`
  = 合并 + 质检 + 渲染 + 字体自检（默认原生可编辑图表；要高质感图加 `--chart-mode mpl`）
- 只渲染已有 deck.json：`python .pi/renderer/render.py <deck.json> -o <out.pptx> --qc`
- 合并（需要中间 deck.json 时才单独跑）：`python .pi/renderer/merge.py <slides_dir> <out.json>`
- 校验（不渲染，只看 schema）：`python .pi/renderer/ppt_dsl.py <deck.json>`
- **禁止**直接调 python-pptx、禁止手写 .pptx XML、禁止 HTML→pptx。

### 输入是 Word（`.docx`）时：先跑一次预处理

```bash
python .pi/renderer/docx_in.py <输入.docx> -o .pi/work/input.md          # 图片落在 .pi/work/media/
```

它一次做完两件事，**别用别的办法凑**：

1. **修订记录不呈现**：按「接受所有修订」的口径处理 —— `w:ins`（插入）内容保留、
   `w:del`（删除）与 `w:moveFrom` 丢弃、批注（`commentRange/Reference`）丢弃，
   格式修订（`*Change`）忽略。也就是说：**写进 PPT 的是"修订接受后"的定稿文字**。
2. **图片原样落盘**：`.pi/work/media/NN-<原名>`，并生成 `.pi/work/input.md.manifest.json`
   （序号 / 格式 / 物理尺寸 / 所在段落）。**EMF / WMF 是矢量图，逐字节原样保留**。

markdown 里图片按原位置留了 `![图N](media/NN-xxx.emf)` 标记，排页时：
- 用 **`figure` 版式** + `image: ".pi/work/media/NN-xxx.emf"` 把它放上页（路径按 `.pi/` 根解析）；
- **不许**把 EMF/WMF 转成 PNG 再嵌、不许重绘（转了必糊；渲染器会逐字节原样嵌入，
  PowerPoint 打开后可无级缩放）。`--qc` 会在图找不到时直接报 error。

## 工作流

0. **输入分析（不可跳过）**：读完全部输入资料后，先做一次结构化分析，把资料拆成
   **章节 → 模块 → 核心结论 → 论据 → 缺口** 五层，写到 `.pi/work/analysis.md`。
   这是"允许优化总结"的**唯一依据**：分析完就知道每页该讲什么、哪些数字必须上页、
   哪里缺料要占位。写完**直接排大纲**（不必停下等确认），只在大纲环节让用户过目一次。

   | 章节 | 模块 | 核心结论（一句判断句） | 论据（数字·口径·限定条件） | 缺口 / 建议补充 |
   |---|---|---|---|---|
   | 2.1 | 三形态演进 | 交互形态每升一档，自主能力就跃升一级 | 典型代表：早期 ChatGPT / RPA、Zapier / Claude Code；口径：2.1 节原始对比表 | 缺各形态的真实任务完成率 |
   | 2.1 | 三形态的局限 | 每个阶段的局限正好是下一阶段要解决的问题 | 无记忆无状态 → 预设路径 → 成本与错误累积 | 无 |

   三条硬规则：

   - **一行一个模块**，不许合并；论据列必须带**具体数字、口径与限定条件**
     （"试点三省存活率 94%"不许写成"存活率 94%"）。
   - 缺口列写清**缺什么、找谁要**（没有缺口也写"无"）——这一列就是后面
     「显式占位」的**来源**，页面上缺的料必须能在这一列找到出处。
   - 分析**允许改写与总结**：把原文的长段落压成一句判断句、合并同类表述都行，
     但**论据条目一条都不许少**，数字、口径、限定条件一律原样保留。

1. **大纲**：先列每页一句话（第 N 页 = slide_type + 标题）。标题必须是判断句。
   **大纲先给用户过目**——尤其是研讨型，页数由资料量决定，方向错了返工最贵。
   **这是全流程唯一一次打断用户**：页数超限要不要拆、讲哪几章、要不要换方向，
   全都并进这一次问完；问完一路做到交付，中间不再问（回炉是照 qc 报告自己改）。
   每页的标题与 `summary` 都要能从 `.pi/work/analysis.md` 的某一行找到依据。
2. **成批生成：一个文件装 5-8 页**（每次 `write_to_file` 都是一次模型往返）——
   同一章/同一节一次写完，写成 `.pi/work/slides/NN-batch.json`，内容是**数组**：

   ```json
   [{"slide_type": "numbered_cards", ...}, {"slide_type": "compare_3col", ...}, ...]
   ```

   **写批次前先出预算表**（大纲定稿后跑一次，整份 deck 共用）：

   ```bash
   python .pi/renderer/budgets.py .pi/work/outline.json -o .pi/work/budgets.md
   ```

   写每一批前先读该批页码对应的预算段：每页**先定条目数再写内容**，定完别改
   （条目数一变该页全部预算作废）；各字段写到**预算目标的 80~90%**、不低于静态下限。
   预算数与 `build.py` 校验出自**同一套几何函数**——照预算写校验必放行
   （`budgets.py --selfcheck` 自证，几何改动后重跑它当回归）。

   `merge.py` / `build.py` 按文件名排序后逐项展开，**一个文件一页的老写法照样能跑**，
   两种可以混用。为什么必须批：40 页按一页一文件写 = 40 次工具调用 = 40 次往返，
   而且每次都要带上"已写的页"，越写越慢；一批 6 页只要 7 次。
   - 一批 5-8 页是经验值：单批输出约 12-20KB；**模型开始截断就降到 3-4 页**，别硬顶。
   - **范例只在开工时读一次**（`examples-all.json` 已含全部 19 个版式）：只有开一个
     **新**版式、或对某个版式拿不准时才单独 Read 那一个范例文件，**别每页读一次**。
   - 一页的素材只从 `.pi/work/analysis.md` 取；**写页时不要回头重读输入原文**
     （分析表就是摘录结果，确实缺料才回去查那一节）。
3. **一条命令出图**（合并 + 质检 + 渲染 + 字体自检，别再分三步敲）：

   ```bash
   python .pi/renderer/build.py .pi/work/slides -o .pi/out/<主题>.pptx \
       --brief seminar --style blue-business --speed slow \
       --source .pi/work/analysis.md
   ```

   - `--check` 只质检不落盘：改完页想先看红线时用它。
   - `--only 3,7` 只渲这几页看版式（页码与整份不一致，**交稿必须整份渲**）。
   - 报告是紧凑 JSON（`errors` / `warnings`），**直接读 stdout，不要再重定向到
     qc_report.txt** —— 那是重复产物，还多一次读写。
   - 渲染很便宜（30 页约 1 秒），贵的是"为了看报告多跑一个回合"——**一批做完再跑一次**。
4. **回炉（按批重写，不要逐页补丁）**：读报告里的 slide/type/field/message，把这一轮
   点名的问题**一次改完**：直接重写它所在的 `NN-batch.json`（一个文件一次写），
   比逐页 `replace_in_file` 少 N-1 次往返；只有"改一句话"这种单点微调才用 `replace_in_file`。
   改完**再跑第 3 步一次**，最多 2 轮。
   **warning 也要处理**：「加粗跨度过长 / 没有标重点 / 加粗占比过高」说明这一页没有重点，
   不是噪音——改完再看一次报告。

`deck.json` 的顶层：

```json
{"title": "主题", "subtitle": "副题", "style": "blue-business", "card": "accent-top",
 "brief": "seminar", "slides": [...]}   # card 可省：省了就用 style 的预设绑定
```

三个顶层字段各管一件事，互不相干：

- `style` = **配色主题**（5 套，见下）——渲染器坐标与配色；
- `card` = **卡片长相**（5 种，见下）——只换卡片怎么画，不动任何文字位置；
- `brief` = **写作方向**（`seminar` 研讨型 / `briefing` 汇报型）——怎么取舍原文。

**两个外观字段都由你自己选，不用问用户**（问一次就多一轮往返）。选完在交付时
说一句"本份用 xx 风格"，用户不满意一句话就能换。

> **用户侧的"PPT 风格"是一个选项，不是两个**：`--style` 选一套配色时，卡片长相
> 按 `theme.STYLE_CARD_PRESET` **自动绑定**（下表最后一列就是绑定值）——
> 25 种组合不该让用户挑。**只有用户明确点名**要换卡片时才额外传 `--card`
> （显式 `--card` 优先于预设）。

| 风格 `--style` | 观感 | 适合 | 绑定卡片 |
|---|---|---|---|
| `style-harness` 经典藏青（默认） | 藏青 + 墨绿/赭金，与历史产出一致 | 拿不准时、延续既有系列 | `flat` |
| `blue-business` 深蓝商务 | 墨蓝 + 石板灰 + 铜金，最克制 | 对上汇报、评审、年度总结 | `accent-top` |
| `bright` 明亮宣讲 | 亮蓝 + 珊瑚橙/薄荷/玫红，活跃 | 宣讲、培训、对外交流 | `outline` |
| `forest` 墨绿战略 | 深墨绿 + 米金/陶土，沉稳 | 战略、能源、可持续、长期规划 | `tinted` |
| `violet-tech` 紫灰科技 | 靛紫 + 青蓝/品红，偏科技 | 产品/技术/平台方案 | `accent-left` |

| 卡片 `--card`（覆盖预设时才用） | 长相 | 适合 |
|---|---|---|
| `flat` | 白卡 + 细描边 + 小圆角 | 与历史产出一致 |
| `outline` 描边通透 | 透明底 + 浅主色描边 + 方角，轻 | 内容偏文字、想让页面"透气" |
| `tinted` 浅色柔块 | 极浅主色底 + 无边 + 大圆角 | 卡片多、想弱化边框的场合 |
| `accent-left` 左侧色条 | 白卡 + 左侧色条 | 清单/条目感强的内容 |
| `accent-top` 顶部色条 | 白卡 + 顶部粗色带 + 无描边 | 栏目感强、要"一眼分区" |

**同一批人连续做的多份 deck 不要每次都落在同一格**（这是"千篇一律"的来源）：
预设已经把配色与卡片**错开搭配**（`bright`+`outline`、`blue-business`+`accent-top`…），
所以换风格优先看受众与内容即可。不写这两个字段 = 经典藏青 + `flat`，
产出与历史版本完全一致。

## 通用质量铁律

- **标题即结论**：每页标题是完整判断句（"统一评测是工程化的第一道闸门"），
  禁止"XX 介绍 / 概述 / 情况 / 分析"这类名词短语。
- **图示优先**：能用 compare_3col / numbered_cards / layered_stack / flow / hierarchy /
  table / chart / panel_2col 表达的，一律不用纯文字页。statement 只用于"结论+论证+关键数据"页。
  一页两块内容 → `panel_2col`（左右两个模块），别用两页各留半页空白。
- **输入里已有的图，用 `figure` 原样放上页**：Word / Visio / draw.io 导出的
  **EMF/WMF 是矢量图**，必须原封不动嵌入（`image` 字段），**不许转 PNG、不许重绘**；
  一页一图（或一图 + 2-3 条要点），比把图里的结构用文字重述一遍有用得多。
- **流程必画 flow**：凡有先后顺序、阶段、生命周期、管道/流水线、决策链路、迭代闭环的内容，
  一律用 `flow`，别塞进 statement 或 numbered_cards——**每份 deck 至少 1–2 页 flow**。
  循环/迭代类内容必须写 `loop_note`（渲染器会画成**环形循环图**：节点绕椭圆一周、
  中心枢纽展示 loop_note、节点间顺时针箭头闭环）。
- **关系必画 hierarchy**：模块之间有「包含/拆分/层级」关系的（A 由 B、C、D 组成），
  用 `hierarchy`（`mode:"contain"` 画树形）；有「递进/升级/阶梯」关系的
  （数据→信息→知识→智慧、能力成熟度 L1→L5）用 `hierarchy`（`mode:"progressive"`）。
  别用一排并列卡片（numbered_cards/layered_stack）硬凑——那表达不了"关系"。
- **比喻化**：compare_3col 的 `metaphor` 必填，技术概念配生活化比喻。
- **底部收束**：有 `footer_note` 字段的版式（statement/compare_3col/layered_stack/chart）
  尽量写一句结论。
- **卡片标题要给右上角图标让位（会压图标 + 折行）**：编号卡的块头是「序号 + 标题 …
  图标」，标题可用宽度已经扣掉图标那一段，所以：
  **5-6 张卡（3 列窄卡）标题 ≤10 字**、4 张卡（2 列）≤20 字；三栏对比的栏名居中排、
  两侧都要让位，**≤8 字**。放不下时渲染器会自动缩半档字号（最低 11.5pt）保住一行，
  但那只是兜底 —— `--qc` 会按原字号点名「标题 N 字放不下（约 X 字/行），会压到图标
  或折成两行」，该砍短就砍短，细节挪进 `desc`。
- **卡片标题即重点（判断句，不是名词）**：无法图表化的内容走「卡片 + 加粗重点 Title」——
  `numbered_cards[].name` 写成**判断句或带数字的结论**（「统一任务集管理」
  「回归通过率 62%→88%」），不要写「任务集管理」「能力建设」这种名词短语：
  名词标题读不出任何结论，却照样占一层高度（再跟一句 `sub` 就是三层开销）。
  `name` 上限 20 字、**`sub` 已改为可选** —— 标题本身已是判断句时就别再补定位句。
  `--qc` 会按「无数字 + 无判断性谓语 + 过短/名词后缀」启发式点名。
- **卡片要有骨架：关键句 + 关键短语**（纯文字卡最容易写成一坨段落，整页"没有特点
  也没有重点"）。骨架**不许靠放大字号**（把关键句提到卡顶放大 + 加细线会把文字顶出
  卡片背景），统一是「**同字号 + 加粗 + 强调色**」：
  - **关键句**：`statement.body` 里**每张卡的第一句**会被渲染器自动加粗染色 ——
    所以第一句要是一句判断（**≤48 字**，带结论或数字），机制与论据放它后面。
    `numbered_cards[].name` / `panel_2col.panels[].summary` 是同一件事。
  - **关键短语**：写 `**短语**：正文…`（`**短语：**正文…` 也认），渲染器把它加粗染成
    强调色、**冒号后的正文在同一段里接着排**。**长文本（>170 字）至少标 2 处**，
    每处一句话说清一件事（如「**判定口径**：…」「**反例**：…」）。
  - **卡片边界用换行指定**：`statement.body` 里用换行（JSON 写 `\n`）分隔每张卡，
    最多 3 张（排成 2 列 × 2 行）；不写换行就按字数自动分 2~3 组。
  - `--qc` 点名「关键句太长」与「长文只有 N 处关键短语」。
- **标题下必有核心结论段（summary）**：每个内容页都在标题下方写 `summary`，
  渲染器会把它放成带浅色边框的浅色块。**五条硬指标，`--qc` 逐条检查**：
  1. **40~80 字**：只留「判断 + 关键数字」。页头是每页最贵的版面（多一行就吃掉
     一整张卡的高度），而它和卡片描述的信息高度重叠 —— **机制细节一律下放到卡片/栏描述**；
  2. **2~3 句**：一句判断 + 1~2 句依据/边界，用句号分开（分号不算句子）；
  3. **禁坐标与自指**：不许出现「1.2 节」「第 4 章」「本节」「原文/原资料」
     「见表」「如图所示」——章节坐标是讲稿里的话，不是 PPT 上的字；
  4. **禁填充语**：「值得注意的是 / 需要指出的是 / 众所周知 / 不难看出 /
     总的来说 / 综上所述 / 可以说 / 本页」这类删掉不影响信息量的词，一个字都别写；
  5. **不复述标题**：标题已经说了判断，结论段要接着讲**依据、口径、边界**，
     换个说法再说一遍等于浪费一整块版面。
  写法：**开口即结论**、主语明确、数字落地，`**...**` 只标最短的判断短语（1-2 处）。
  写完自查一句：**把这段拿掉，读者少知道的正好是这一页的结论吗？**
- **加粗要精炼**：重点**只能**靠 `**...**` 标出来 —— 渲染器**不会**再自动把首句加粗。
  每页标 **1-2 处**、每处 **≤16 字**（关键词或最短的判断句）；整句加粗、大段加粗
  会被 `--qc` 报 warning：**整句加粗等于没加粗**。statement 的 `body` 不写 `**`
  就会被提示"这一页没有任何重点"。
- **一页至少两个信息块**（密度第一铁律）：密度上不去从来不是"没写满"，而是
  **整页只有一个容器**。每个版式都有第二个位置，用它装主内容放不下的信息：
  - 表格页 → `side`（右侧 0-4 条：关键数字 / 边界条件 / 待确认点），表格会自动收窄；
  - 图表页 → `detail_headers` + `detail_rows`（数据点 ≤5 时**必须**补一张明细表：
    指标 / 目标值 / 口径 / 验证方式），图表高度也会随之变紧凑；
  - 卡片型（compare_3col / numbered_cards / layered_stack / flow / hierarchy / panel_2col）→
    `callout`（底部横排 2-4 条关键数字或待确认点）。
  `--qc` 会逐页点名"只有一组卡片/一张表"的页面。
- **两块内容一律左右分置，不许上下堆叠**：一页要放两块内容时，**左右并排**
  （`panel_2col` 两个模块，或表格用 `side`、图表用右侧洞察），
  **不要**上半页一块、下半页一块 —— 上下堆叠几乎必然在下半页留下半页空白，
  这是密度上不去最常见的原因。`--qc` 会报"下半页还空多少"。
  **`callout` 的落位是渲染器算的、你不管**：渲染器会优先把它放进**右侧纵栏**
  （`flow` 环形、`layered_stack`、4 张编号卡都走右栏 —— 底部横条会把环压扁、
  把堆栈条挤矮）；只有主内容**必须靠宽度才成立**时才退回底部横条
  （≥5 步线性流程、5-6 张编号卡、`compare_3col`、`hierarchy`、`panel_2col`）。
  想让主内容更完整就往右栏走：少写 `callout`、改写成 `footer_note` 也行。
- **每个模块独立背景框 + 模块顶部一段总结陈述段**：模块（卡片/栏/层/步骤/节点/
  `panel_2col` 的 panel）必须各自一个框，框内**顶部先给一段总结陈述段**
  （`panel_2col.panels[].summary` / `compare_3col.columns[].tag`+`desc` /
  `numbered_cards[].sub`+`desc`），再往下才是明细。总结陈述段写这一模块的
  **判断 + 依据**（带数字或口径），不是标题的复述。
- **版式上限只约束"一页摆多少"，不约束"总共讲多少"**：条目超出上限时**另起一页继续**，
  **绝不许删条目**（`schema` 报错信息里都写了这句）。上限已按**真实几何容量**放宽：
  `flow` **3–12 步**（>6 步自动两行折返）、`layered_stack` **3–12 层**（层多间距自动压紧）、
  `numbered_cards` **4–8 张**（7-8 张排 4 列、窄卡不画图标）、`hierarchy` **2–8 个**、
  `compare_3col` **3–4 栏**、`table` **≤12 行**、`toc` 3–6 章（更多就再写一页目录）。
  **"为了页数好看而删内容"是本项目最严重的错误** —— 页数少 ≠ 密度高。
- **内容太少就并页，不要留白**（并页优先于补排版）：出现下列任一情况，
  **先把相邻页的同主题内容并进来**，而不是把这一页交出去：
  - 表格 < 5 行、图表数据点 ≤ 4 且补不出明细表、卡片 < 4 张、`panel_2col` 单侧
    要点 < 3 条；
  - `--qc` 报"主表下方还空 X in / 下半页还空 X in / 两个模块还剩 X in"。
  两块内容原本分属两页时，**并成一页用 `panel_2col` 左右并排**（每块一个模块，
  各带自己的背景框与总结陈述段），比两页各留半页空白强得多。
  原文确实没有对应资料 → 补一行「待补」显式占位（写清缺什么、找谁要）。
- **正文不许精简过头**（与"高密度"同等重要）：高密度 = **单位版面信息多**，
  不是字少。`statement.body` ≥ 150 字且是连贯段落；`compare_3col` 每栏 desc ≥ 45 字；
  `numbered_cards` 每卡 desc ≥ 40 字；`layered_stack` 每层 desc ≥ 30 字；
  `flow` 每步 desc ≥ 16 字；`hierarchy` 每个 node.desc ≥ 20 字。
  改写、润色、合并同类句都可以，但**把论据/机制/口径压成短语就是抽干信息**，
  `--qc` 会逐页点名"精简过头"。
- **图表可再紧凑一档**：图表高度按数据点自适应（数据点少就矮），省下来的高度
  交给明细表或右侧洞察卡，别让图表霸占半页、下面留白。
  类别名较长（>4 字）时优先 `bar`（横向条）而不是 `column`，避免标签挤成一团。
- **放不下是渲染器的事，不是你的事**：正文/描述/单元格会自动逐档降字号
  （11.5 → 11 → 10.5 → **10pt**；层级图另有 9.5/9 的小档），`--qc` 只在
  "降到最小档仍放不下"时才点名，并把降档页列在 `stats.downshifted` 里。
  所以**下限面前写满比写短安全** —— 不要为了"怕溢出"把论据压成短语，
  那正好把密度又还回去了。**上限面前看预算表**：写到预算目标的 80~90%，
  顶格写满静态 `max_length` 正是"长度类校验错误"的主要来源。
  真写不下时该做的是并页/拆页，不是删字。
- **但"一个框里塞太多"仍然是错**：容器是硬的，渲染器不会让内容画出框，只会把字号、
  行高压到可读下限以下（`--qc` 会点名「模块内容超出模块框 X in」/「单元格文字会撑行」）。
  两条经验规则：`panel_2col` 的一个模块里 **要点 + 迷你表行数** 加起来不要超过
  "6 条要点"或"8 行明细"的量级；`table` 行数多（>8 行）时**单元格必须短**
  （每格 ≤ 一行的量），否则行高被压到放不下文字，PowerPoint 打开时会把行撑开、
  把底部 `note` 压住。超了就**另起一页**，不要挤。
- **表格列必须有信息量**：整列同一个值的列（典型是「原文出处」「来源」）**删掉**，
  出处写进 `note` 一句话带过；列宽已按内容自适应，短列不必凑字数。
- **铺满靠补内容，不靠拉高排版**：内容页不留大片空白，但留白**不许**用「拉高行高」
  「拉长卡片」硬撑。正确做法是把**下一章节或关联章节的内容并到本页**（表格加行、
  卡片加要点、**两页并成一页用 `panel_2col` 左右并排**），写到**接近但不超过**安全上限。
  补内容时先回 `.pi/work/analysis.md` 看同一模块的论据列还有哪些没上页——留白通常是
  "论据没搬完"，不是"页面太大"。
  原文确实没有对应资料时 → **显式占位**：表里补一行（首列写「待补」＋缺什么、找谁要），
  或用 `note` / `footer_note` 写明缺口，让读者一眼看到还缺什么，别拿空白糊过去。
  `--qc` 会给表格页算出「只占多少、还空多少、大约还能放几行」。
- **图标一块一个**：每个「内容块」（卡片/栏/层/步骤/节点/洞察）只配**一个** `icon`，
  画在块头；**块里的大段文字前面不要再放图标**——渲染器一块只画一个，
  块头已经有图标时，正文前不会（也不该）再补第二个，两个图标会互相打架。
  没写 `icon` 的块渲染器会按文字自动补一个，所以漏填不会出现"光秃秃的框"，
  但别依赖它。

| matrix | title 6–32（判断句）· summary 40–80 · **col_labels 2–4** 每个≤8 · **rows 2–4**{label≤8, cells 数=列数{title 2–16, desc 4–90, icon}} · footer_note≤64（两维交叉分类用，grid_2x2 的 m×n 泛化；不支持 callout） |
| grid_2x2 | title 6–32（判断句）· summary 40–80 · **四方格固定 2×2**{title 2–12, **value≤14**（核心指标，18pt 大字，必须有数字）, desc≤60（一句话说明）, icon} · footer_note≤64（四象限/SWOT/重要-紧急矩阵用；不支持 callout） |
| key_groups | title 6–32（判断句）· summary 40–80 · **groups 2–4**{title 2–18（判断句/带重点，别用纯名词）, **points 2–6** 每条 4–60（「结论 + 数字/口径」）, icon} · **callout 0–4** · footer_note≤64（**平行主题组**的正身：分组但不对比、成组但没顺序；statement 的前置选项） |

**容量是动态算出来的，不背数字**：同一个 `desc` 字段，4 张卡时可写 240 字、
8 张卡带辅区只有 90 字——动态数字有两个出处、**同一套几何**：
- **写之前**：预算表（`budgets.py`，见工作流第 2 步）逐页下发，按它写
  （目标 80~90%）——照预算写校验必放行；
- **写之后**：`--qc` 报「这个框约能写 X 字」——回炉时以它为准。
- schema 的 `max_length`（上表）是**最宽松情形**的兜底值，顶格写它就是
  长度类返工的来源；"写满比写短安全"指的是**下限**（密度红线）方向，
  不是顶格写静态上限。

**下限也是硬指标**（对应"-qc 点名"）：statement.body ≥ 150、compare 每栏 desc ≥ 45、
numbered_cards 每卡 desc ≥ 40、layered_stack 每层 desc ≥ 30、flow 每步 desc ≥ 16、
hierarchy 每个 node.desc ≥ 20、`panel_2col` 每个模块 summary ≥ 16、
timeline 每个节点 desc ≥ 25、funnel 每层 desc ≥ 20、matrix 每格 desc ≥ 15、
key_groups 每条要点 ≥ 8。
**写到接近上限、不要贴着下限**，下限只是"精简过头"的红线。

**compare_3col 的 desc 另有一条动态上限**：它取决于本页 `summary` 几行、这一栏有几条
`points`（描述下面还要摆要点和比喻条）。页头结论段越长、要点越多，描述能写的字越少，
实测 80~260 字之间浮动。拿不准就少写描述、把内容放 `points` 里，`--qc` 会给准确数字。

## 图标

**一个内容块只配一个图标**（见上面的「图标一块一个」）：块自带 `icon` 就用它，
没写就由渲染器按文字自动挑一个补在块头。**不要在正文里再插图标**，
也不要把同一语义的图标在块头和正文前各画一次。

`icon` 填 **Tabler 英文名**（如 `settings-2` / `chart-bar` / `shield-lock` / `trending-up` /
`git-fork` / `box` / `database` / `route-2` / `refresh` / `rocket` / `versions` / `upload`）或
**中文别名**（见 `.pi/assets/icons/aliases.json`，常用：工程/齿轮、安全、协作、增长、分析、告警、
云、数据库、引擎、报告、上传、执行、决策、可观测、目标、亮点、工具、发布、版本、编辑、压缩、层次、缺口）。
**同一页里别清一色用同一个图标**，按每块的实际语义分开选。

**图标名必须是登记过的**：写错的名字（自造的中文词）渲染器会**兜底**（按块内文字自动补
一个、再退到通用图标），但 `--qc` 会逐页点名——兜底只保证"不缺图"，语义是你自己丢的。
拿不准就填英文名，或先看 `aliases.json` 里有没有对应中文别名。

## 边界

- 全程中文（简体）。
- 内网无外网：不下载图片/依赖；缺素材就画结构图或用文字。
- **外观只在 deck 顶层选，页面里不许写颜色**：配色只认上表 5 个 `style` 名、
  卡片只认 5 个 `card` 名，**自造名字会被确定性回退**（回退默认值 + `--qc` 出 warning，
  所以你换了等于没换）。逐页 DSL 里**不要**出现任何颜色/字体/主题参数 ——
  外观只归 `theme.py` 管，别在页面里写 hex、也别建议"这一页用红色"。
- **字体不用你管，也不许你指定**：渲染器统一写死「中文微软雅黑 + 西文 Times New Roman」
  （都是系统自带，仓库不带字体包）。别去改字号字体、别提"换成某字体"这类建议 ——
  字体是外观主题的一部分，改它要改 `.pi/renderer/theme.py`，不是改 deck.json。
- **放不下是拆页，不是删原文数字或限定条件。**
- 命令失败先读报错再改，禁止盲目重试超过 2 次。

## 范例：开工读一次 `examples-all.json`

`examples-all.json` 是 19 个版式范例**合并成的整份参考 deck**（19 页），
每个版式的写法（判断句标题、关键句、`**关键短语**：`、密度、图标、收尾）都在里面。
**开工时一次读完它**，按版式对号入座；要抠某个版式的细节再单独读 `examples/NN-*.json`
（**只在开新版式、或拿不准时才读**——它不是每页的必读项，见工作流第 2 步）。

> 不要"生成一页就读一个范例文件"：40 页 deck 会白搭 40 次读盘与上下文，明显拖慢出稿。
> `examples/` 目录本身也可以随时合并成整份（改动范例后重生成）：
>
> ```bash
> python .pi/renderer/merge.py .pi/skills/ppt-common/examples .pi/skills/ppt-common/examples-all.json --title "版式范例合集"
> ```
