# `.pi/out/Harness工程_v23_高密度_错误样例示范.pptx` 两处溢出的根因分析与修复

> 结论先行：**这两处都不是"内容写多了"，而是渲染器的几何算法在有界空间内没有"上收"的机制。**
> 可复算的实测数据、修复落点与回归入口都在本文；长期规则已写进
> [`pitfalls.md`](pitfalls.md) 的第 21 / 22 条。

## 一、P3：`panel_2col` 右模块的迷你表被挤出框

### 根因（代码级）

`render_panel_2col` 旧算法是**自上而下**画的：要点先画，迷你表再按"剩余空间"落位。
两个地方一起出事：

1. `_panel_points` 用 `pick_step` 挑字号，而 `pick_step` **在最小档也放不下时照样返回最小档**
   （设计如此：渲染绝不失败）—— 要点越界，把表一路往下顶；
2. `_panel_table` 用 `row_h = max(0.18, (avail-head)/n)` 给行高兜底、
   `ty = y + max(0, (avail-total)/2)` **从不上收** —— `total > avail` 时就整块画到框外。

### 实测

| | 模块卡片 | 该模块内的迷你表 | 结果 |
|---|---|---|---|
| v23 成品（python-pptx 读回） | top 2.006 / h 3.828 → **底 5.834** | top 4.739 / h 1.256 → **底 5.995**，行高 `0.34 + 4×0.229` | **越出 0.161 in** |
| 现行代码 + 3 条要点（修复前） | 同上 | top 4.866 / h 1.06 → 底 5.926 | 越出 0.092 in |
| 修复后 | 同上 | top 4.779 / h 0.876 → 底 **5.654**（= 内容区下沿 `cy_bottom`） | 框内，与要点留 0.22 in |

`panel_slack()`（"自然需要 − 可用"）在修复前是 **−0.342**（P3 原样例，3 条要点时 −1.059）：
**内容本来就超框，但旧 qc 只在 slack > 0.80 时点名，负值静默通过** —— 这才是它能一路交出去的原因。

### 修复

`panel_content_geom()` 成为模块内唯一的几何口径：

```
[cy, cy_bottom] 内
  1. 迷你表按内容要一个自然高度，最多只拿 avail − 要点最小高度 − 间距；
  2. 表【底部锚定】在 cy_bottom，head_h + row_h×n ≡ tbl_h —— 不可能越框；
  3. 要点只在上方剩余区间里排（真放不下就继续降字号，下限 7.5pt）。
```

要点字号 / 行高 / 间距都由这一个函数产出，渲染与 qc 共用。

## 二、P4：表格页整体出界 + 底部 note 压住表格

### 根因（三条叠加）

1. **行高写死**：`body_h = TABLE_ROW_H(0.46)`，不按可用高度压紧 → 11 行 = 5.56in；
2. **note 被夹到页底**：`ny = min(max(表底, 辅区底边) + 0.08, BODY_BOTTOM - note_h)`
   —— 右侧辅区比表高时会把 note 往页面底部推，正好压在表上；
3. **隐性成因**：python-pptx 写进 `a:tr@h` 的行高只是"**最小**高度"，单元格文字放不下时
   PowerPoint 会**自己把行撑高**，撑开的部分没人回收 —— 所以"把行高压小"并不等于把表压进页面。

### 实测

```
旧算法（行高不压紧）：table top=2.096  h=5.56   bottom=7.656   行高 [0.5, 0.46, 0.46, …]（11 行）
v23 成品            ：table top=2.096  h=5.56   bottom=7.656   行高 [0.5, 0.46, 0.46, …]（11 行）  ← 完全一致
v23 成品            ：note top=6.376 → 与表格重叠 1.28 in
现行代码（行高已压紧）：top=2.096  h=4.164  bottom=6.26，note 6.34–6.78（不重叠）
```

`BODY_BOTTOM = 6.80`、页高 `7.5` —— 表底 7.656 已经跑到页面外。

### 修复

`table_geom()` 统一算出 `head_h` / `body_h` / `cell_size` / `total_h` / `note_y`：

- `head_h` 随可用高度收，保证 `total_h ≤ avail`；
- 新增 `table_row_need()`（文字自然高度 + 上下内边距），字号从 `TABLE_CELL_STEPS`
  （11.5 → 8.5pt）**反推**，确保 `body_h ≥ 自然高度`，PowerPoint 不会撑行；
- `note_y = 表格底边 + 0.08`，**不再和辅区底边取 max**。

## 三、新增的机检（只出 warning，不拦渲染）

| 检查 | 触发条件 | 文案要点 |
|---|---|---|
| `panel_2col.panels` | 模块内容超出框，要点被压到 < 9.5pt 或迷你表行高 < 0.18in | 「删一条要点或几行明细；明细 > 8 行 / 要点 > 6 条就该另起一页」 |
| `table.rows` | 最小字号档下单元格文字仍高出 `body_h` > 0.02in | 「PowerPoint 打开时会把行撑开，整张表会溢出内容区并压住底部 note」 |

## 四、关于"另一台离线电脑"

- v23 的 P4 行高（`0.5 + 11×0.46`）与"行高不 clamp"的**旧实现逐位吻合**；
- v23 的 P3 表（`0.34 + 4×0.229`、`ty = 4.739`）与当前代码的任何分支都对不上
  （当前代码对应 `bottom` 是 5.654，不是 5.995）。

**建议**：先核对那台机器上 `.pi/renderer/layouts.py` 的版本 / 文件时间 —— P4 大概率是
**旧的未 clamp 版本**（离线机器不会自动同步）；P3 那一页更像是在 PowerPoint 里
**手工加了一行文字 + 把表拖下去**做出的示范。两条路径本轮都已堵死。

## 六、遗留（未改，供决策）

图表页下方明细表（`chart.detail_rows`）用的是另一套行高公式
（`chart_metrics` 的 `d_row = min(0.46, max(0.24, …))`，字号固定 10pt），
存在与 P4 **同源**的风险（行高低于文字自然高度时 PowerPoint 会撑行）。
本轮未动（用户报的两处已覆盖），建议下一轮按 `table_geom` 的做法统一。
